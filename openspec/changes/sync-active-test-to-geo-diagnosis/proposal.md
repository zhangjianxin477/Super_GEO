# Proposal

## Why

当前 03「GEO 诊断与基线」会从项目历史测试中猜测一条批次作为数据源。当同一项目已运行过旧测试且旧测试包含审核证据时，03 会读取旧批次而非 02「真实平台测试」正在使用的当前批次，导致已回传、已批准的数据在诊断页不可见。

需要把 02 定义为每个项目唯一的正式诊断数据源：测试回传和审核完成后，03 自动读取同一项目当前批次并刷新进度、证据状态和正式指标，而不要求用户理解 Test Run 或手动同步。

## What Changes

- 为每个项目维护内部的“当前真实平台测试批次”指针，并限制在相同工作区与项目内。
- 新建 02 测试时自动设为当前批次；向该测试追加平台时持续使用同一批次，避免历史小批次覆盖当前数据。
- 让 03 GEO 诊断只读取项目当前批次，不再按“最早已审核 / 首个有回答”的历史猜测选择数据源。
- 在 03 展示当前 02 数据源的 Query、平台、已回传、待审核、已批准和最近更新时间。
- 保持证据边界：仅已批准回答计入正式品牌提及、推荐表达、自有链接引用和来源收录指标；已回传未审核回答只展示进度与“待审核”状态。
- 在 02 明确标识“本项目当前 GEO 测试批次”，并说明批准后的证据会自动刷新 03。
- 为同项目多批次、跨项目隔离、回传与审核后的自动刷新补充服务端和前端测试。

## Capabilities

### New Capabilities
- `active-real-surface-diagnosis-sync`: 将当前项目的真实平台测试批次作为 GEO 诊断唯一自动数据源，并在回传、审核后更新诊断数据状态与指标。

### Modified Capabilities
- None.

## Impact

- 数据库：项目诊断案例增加当前真实平台测试批次关联，并提供迁移与数据回填规则。
- 服务端：`server/repositories/harnessRepository.mjs`、`server/application.mjs` 的测试批次创建、查询与项目诊断接口。
- 前端：`src/api.ts`、`src/BaselineWorkspace.tsx`、`src/VisibilityBaseline.tsx`。
- 测试：真实平台测试 API、诊断基线与可见度指标相关测试。
