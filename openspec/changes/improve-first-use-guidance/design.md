# Design

## Context

现有 React 单页应用已能从本地 API 读取市场包、评估、任务与受控人工回答证据，也已有未完成任务的恢复能力。当前障碍集中在工作流可理解性：导航暴露了许多需要前置条件的页面；已领取任务仅以文字提示“打开平台”；首个采集目标与后续依赖页之间缺少持续的、口语化的指引。

## Goals / Non-Goals

**Goals:**
- 将首用路径压缩为“确认当前阶段 → 采集一条回答 → 保存证据”的可视化操作闭环。
- 为各受支持的国内外 AI 平台维护静态、可审查的官方入口映射。
- 在不完整阶段给出一致的恢复按钮和清晰原因。
- 保留现有数据模型、租户隔离、审计和受控人工边界。

**Non-Goals:**
- 不自动登录、执行、抓取、导入或发布到第三方平台。
- 不生成伪造回答、虚构评估结论或为了演示而污染真实的工作区数据。
- 不改变后端评估、诊断、内容审批或报告生成的准入条件。

## Decisions

### 1. 以客户端操作指引作为渐进式披露层
在仪表盘和采集页复用一个轻量的工作流提示组件，而不是引入新的后端状态或全屏、不可跳过的新手教程。它根据现有评估完成度和已领取任务确定显示内容。

**Rationale:** 现有 API 已拥有可信的评估与任务状态；增加教程持久化会引入与真实流程不同步的第二状态源。

**Alternative considered:** 强制分步遮罩教程。未采用，因为企业操作者常需切换页面检查资料，强制遮罩会妨碍既有用户并掩盖真正的流程状态。

### 2. 采用静态、显式的官方入口映射
在前端维护已支持 Provider 的官方站点映射。没有映射的平台不显示可点击链接，并提供清晰的人工打开说明。

**Rationale:** 不需要保存用户凭据、请求第三方 API 或引入不透明跳转；映射可被代码审查和单元测试覆盖。

**Alternative considered:** 后端存储可编辑入口。未采用，因为当前没有租户级 Provider 配置需求，引入后端可编辑 URL 会扩大安全审核范围。

### 3. 为流程门槛复用单一恢复卡片
分析、内容、报告等依赖页面使用统一的 gate 表达“为什么还不能继续”和“现在应该去哪里”，只展示一个主操作。

**Rationale:** 减少选择负担，并避免把无数据状态误解为故障。

## Risks / Trade-offs

- [静态链接变更] → 使用官方根域名或稳定入口并保持 Provider 映射集中，后续可单点审查。
- [少量操作提示增加页面密度] → 仅在评估不完整或有活动任务时展示，完成后自然退化为普通仪表盘。
- [用户在外部平台完成提问后返回] → 保持本地表单和任务恢复机制，不依赖浏览器返回事件。

## Migration Plan

1. 添加首用指引、平台入口和流程 gate 复制文案。
2. 添加前端回归测试，并执行完整验证套件。
3. 在本地运行实例中冒烟验证：领取/恢复任务、打开平台入口、刷新保留任务、从 gate 返回采集页。
4. 如需回滚，仅移除前端提示与链接；后端数据和任务状态不受影响。
